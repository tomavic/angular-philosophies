Philosophy

Build only what is needed, put each kind of code in one place, and make the right thing the easy thing.

This is how I write Angular apps, written down so a team, a new hire or an AI agent can write them the same way. It targets Angular 22 with TypeScript 6.0, zoneless, signals everywhere, NgRx SignalStore for state, and an Nx workspace split by business domain.

It is a set of defaults, not a law. Every rule comes with the reason behind it, so you can tell when your situation is different enough to break one.

Code is a necessary evil

Every line you write is a line someone reads, tests, upgrades and eventually deletes. The best change is the one you didn't have to make, and the second best is the smallest one that works.

  • Build what is needed today. YAGNI is the most useful rule I know. A flag, a config option or an abstraction for a case that might come later usually costs more than adding it later, because later you know what the case really is.
  • Don't be clever. Clever code is read at 3am by someone who didn't write it. Boring and obvious wins.
  • Think before adding a dependency. If the platform does it, use the platform. Angular 22 already ships httpResource, signal inputs, linkedSignal, a router, forms and a control flow syntax. Reach for a library when the problem is real, not when the tutorial used one.
  • Delete before you add. Removing unused code, an old wrapper or a flag nobody sets is progress.
  • Write an abstraction the third time, not the first. Two copies are cheaper than the wrong shared function. This is also how the custom store features in 06-custom-features.md are meant to appear.

Leave it better than you found it

When you touch a file, fix the small smell next to your change or leave a TODO with a reason. Don't start a rewrite inside a feature branch. Refactor in small steps with the tests green, and make the next person's change easier than yours was.

One place for each thing

Most arguments about structure go away when each kind of code has exactly one home:

  • Server state, API calls and the facade a page talks to live in a signal store.
  • A page's markup and its wiring live in a component.
  • Anything two features need lives in a library with a tag that says what it may depend on.
  • A rule a machine can check is a lint rule, not a paragraph in a wiki.

01-architecture.md and 03-signal-store.md are these ideas made specific.

Make the right thing the easy thing

Conventions only survive if following them is less work than ignoring them. That is why this repo ships templates (a store, a test toolkit, config files) and AI instructions as well as prose. Copy the template, change the names, and you are already following the guide.

Accessibility and Arabic are not extras

A page that can't be used with a keyboard, or can't be read at arm's length, is not finished. A layout that breaks in right-to-left is not finished either. Both are cheap to do from the first commit and expensive to retrofit, so they are part of the defaults. See 07-forms-routing-i18n.md and 08-accessibility.md.

Rules

These are the lines your AI tool receives. Each one is a sentence on its own.

  1. Build only what the current task needs; do not add flags, options or abstractions for hypothetical cases.
  2. Prefer the Angular platform (httpResource, signal APIs, router, forms) over a new dependency.
  3. Write a shared abstraction the third time the same code appears, not the first.
  4. When touching a file, fix nearby smells or leave a TODO with a reason; never rewrite inside a feature branch.
  5. Express every rule a machine can check as a lint rule or a type, not as documentation.
  6. Treat accessibility and right-to-left support as part of "done", not as follow-up work.
